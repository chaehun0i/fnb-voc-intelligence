# Day 15 ServIQ 프론트엔드 사용자 경험

## 목적

Day 13의 운영 화면과 Mock Contract, Day 14의 Incident API 경계를 이어서 사용자가 실제로 이슈를 읽고 처리할 수 있는 한국어 운영 콘솔을 구성합니다. 화면 외형뿐 아니라 증거·원인·조치·검증의 내부 내용, 검토 사유, 연동 상태, 작업 실패와 설정 이력까지 확인할 수 있도록 보강합니다.

화면은 서버 또는 Mock API가 제공한 Permission의 허용 여부와 이유를 표시합니다. 인시던트의 상태 전이는 Domain/Application 계층에서 결정합니다. 기존 Streamlit Dashboard와 RAG·ingestion 기능은 별도로 유지합니다.

## 구성

### 공통 화면과 조작

- 상단 바와 사이드 메뉴는 고정하고 각 페이지의 본문만 스크롤합니다. 다른 메뉴로 이동하면 새 페이지를 맨 위에서 보여 줍니다.
- 선택한 메뉴는 배경과 아이콘으로 구분하고 `aria-current`로 현재 페이지를 전달합니다.
- 키보드 조작 시 `본문 바로가기`를 사용하면 현재 페이지와 주소를 유지한 채 본문에 포커스를 둡니다.
- 인시던트 상세는 목록 위의 `Radix Dialog`로 열립니다. 헤더와 닫기 버튼은 유지하며 긴 본문만 스크롤합니다. `ESC`, 배경 클릭과 닫기 버튼으로 목록에 돌아옵니다.
- `Radix Select`로 필터와 운영 명령을 선택합니다. 긴 선택 목록은 최대 높이 안에서 스크롤하며 키보드로 선택할 수 있습니다.
- 표는 좁은 화면에서 가로 스크롤합니다. 사이드 메뉴는 좁은 화면에서 아이콘 중심으로 축소하고 버튼의 접근 가능한 이름을 유지합니다.
- 버튼의 기본·주요 작업·주의 작업·비활성 상태, 입력값 오류, 로딩·오류·빈 결과를 일관되게 표현합니다.
- 시각과 날짜는 한국 시간으로 표시합니다. 값이 없거나 올바르지 않으면 `기록 없음`으로 안내합니다.
- 메뉴 전환에는 `Framer Motion`의 짧은 진입 효과를 사용합니다. 기기의 모션 감소 설정을 적용하면 이동 효과를 줄입니다.

`Tailwind CSS`와 공통 스타일을 함께 사용하며, `lucide-react` 아이콘은 메뉴와 업무 의미를 보조합니다. 필터·팝업·상세 탭의 조작은 Radix 컴포넌트로 구성합니다.

### 화면 주소와 이동

메뉴마다 `/#/dashboard`, `/#/incidents`, `/#/reviews`, `/#/trace`, `/#/integrations`, `/#/queue`, `/#/settings` 주소를 사용합니다. 별도 라우팅 라이브러리 없이 브라우저의 hash와 `hashchange` 이벤트를 사용하며, 알 수 없는 경로는 운영 대시보드를 표시합니다.

인시던트를 선택하면 현재 페이지 주소에 `?incident=<인시던트 ID>`를 추가합니다. 예를 들어 `/#/incidents?incident=inc-1`을 직접 열거나 새로고침하면 인시던트 목록 위에 해당 상세 팝업을 엽니다. 대시보드에서 선택하면 대시보드 주소와 배경을 유지합니다. ID는 URL 인코딩하여 전달합니다.

팝업을 닫으면 현재 메뉴 주소에서 인시던트 ID를 제거합니다. 브라우저의 뒤로가기·앞으로가기는 이전·다음 주소에 기록된 메뉴와 상세 선택을 다시 표시합니다. 주소는 메뉴와 인시던트 선택만 포함하며, 목록 필터·검색어·상세 탭·저장하지 않은 입력까지 복원하지는 않습니다. Mock 데이터의 변경 결과는 주소와 별개로 새로고침 시 초기화됩니다.

### 최초 진입 로딩과 빌드 분할

각 페이지와 인시던트 상세는 `React.lazy`로 필요한 시점에 불러옵니다. 공통 App Shell은 유지하고, 페이지 코드가 준비되는 동안 본문에 `화면을 준비하는 중입니다`를 표시합니다. 이어서 각 페이지의 API 요청 상태에 맞는 로딩·오류·빈 결과를 보여 줍니다.

Vite의 production build는 대시보드, 인시던트 목록·상세, 검토, 실행 추적, 연동, 대기열과 설정을 별도 JavaScript 청크로 나눕니다. 모든 화면 코드를 최초 진입에 한꺼번에 받지 않는 구조이며, 페이지를 처음 열 때 해당 청크를 추가로 불러옵니다. 실제 전송량과 진입 속도는 선택한 화면, 공통 청크 캐시와 네트워크 상태에 따라 달라집니다. 개발 서버의 모듈 로딩 시간과 production build의 성능을 동일한 값으로 기록하지 않습니다.

심각도·상태 배지는 `components/IncidentBadge.tsx`에서 공통으로 사용합니다. 배지를 표시하려고 다른 기능의 페이지 전체를 import하지 않으므로, 대시보드나 검토 화면에 불필요한 인시던트 목록·등록 코드를 함께 연결하지 않습니다.

### 페이지 오류와 복구

페이지 파일 다운로드나 렌더링이 실패하면 `PageErrorBoundary`가 본문을 한글 오류 안내와 `전체 화면 새로고침` 버튼으로 바꿉니다. 상단 바와 메뉴는 유지하며 내부 오류 문자열이나 stack을 화면에 표시하지 않습니다. 메뉴가 바뀌면 오류 상태를 초기화하여 다른 화면을 열 수 있습니다.

이미 실패한 lazy 파일을 같은 화면에서 재사용하면 다시 실패할 수 있으므로, 연결 문제를 해소한 뒤 전체 새로고침으로 파일을 다시 불러옵니다. 전체 새로고침은 저장하지 않은 입력과 Mock 변경 내용을 초기화합니다. API 요청 오류는 각 페이지의 요청 상태에서 처리하며, 이 경계가 등록·승인 등 운영 명령을 자동으로 재실행하지는 않습니다.

### Incident Mock/HTTP 경계

기본 `mock` 모드는 화면 검토용 예시를 제공합니다. 검토·연동·대기열·설정의 작업은 Mock API에 반영되고 새로고침하면 초기 예시로 돌아갑니다.

`http` 모드의 Incident는 FastAPI에 목록·상세·Workspace를 요청합니다. 등록과 분류, 조사 시작, 증거·원인 분석·조치 등록, 승인 요청·승인·반려, 수동 실행 완료 기록, 검증·종결·재발 명령을 서버에 전달합니다. 명령 버튼은 서버 Permission과 처리 중 상태를 반영합니다. 충돌이나 오류에는 API의 안내와 요청 식별자를 표시합니다.

인시던트 목록의 경과 시간은 HTTP 모드에서 화면을 표시하는 현재 시각을 사용합니다. Mock 모드는 예시 데이터의 고정 기준 시각을 사용하므로 날짜가 달라져도 같은 예시를 확인할 수 있습니다. 이는 시간 표시 기준이며 상태 전이나 SLA 정책을 프론트에서 결정하는 규칙이 아닙니다.

## 실행 및 검증

저장소의 `frontend/` 디렉터리에서 잠금 파일에 맞춰 의존성을 설치합니다.

```bash
npm ci
npm run dev
npm run lint
npm run test
npm run build
```

기본 미리보기는 추가 환경 설정 없이 실행합니다. 명시적으로 설정하려면 `frontend/.env.local`에 작성합니다.

```dotenv
VITE_API_MODE=mock
```

실제 Incident API에 연결할 때는 다음 값을 사용합니다. 환경 값을 바꾼 뒤 개발 서버를 다시 실행합니다.

```dotenv
VITE_API_MODE=http
VITE_API_BASE_URL=http://localhost:8000/api/v1
```

API 실행과 저장소 설정은 [Incident Domain API](serviq_incident_api.md), [Incident 영속화와 Outbox](serviq_persistence.md)를 확인합니다.

프론트 테스트는 화면 렌더링·팝업, 공유한 hash 주소에서의 상세 접근, 본문 바로가기의 주소·포커스 유지, Mock/HTTP Adapter, 오류 변환, 검토·설정 변경, 연동·대기열 동작과 실행 추적을 검증합니다. HTTP 경과 시간 테스트는 현재 시각을 고정하고 Mock 표시도 별도로 확인합니다. 최초 lazy 화면의 준비를 기다린 뒤 내용이 표시되는지 검증하며, 테스트를 통과시키기 위해 본문 검증을 생략하지 않습니다. 페이지 오류 테스트는 실패하는 자식 화면으로 한글 안내·내부 오류 비노출·다른 메뉴로 전환한 뒤 복구를 확인합니다.

화면 검토에서는 메뉴 주소를 복사하여 직접 열기, 상세 팝업에서 새로고침과 뒤로가기·앞으로가기, 긴 선택 목록의 스크롤, 상세 본문 스크롤 중 헤더 유지, 키보드 포커스, 오류·빈 상태와 좁은 폭의 표를 함께 확인합니다. `npm run build` 결과에서 페이지별 청크가 생성되는지도 확인합니다.

## 제한 사항

- 대시보드·검토·실행 추적·연동·작업 대기열·운영 설정은 아직 Mock Contract를 사용합니다. Incident를 HTTP 모드로 바꾸어도 이 페이지들이 실시간 운영 데이터로 바뀌지는 않습니다.
- 설정 저장과 복원, 검토 결정, 동기화·대기열 미리보기는 현재 브라우저 실행의 메모리에 반영됩니다. 서버 저장이나 외부 시스템 변경으로 이어지지 않습니다.
- Incident의 수동 실행 완료 명령은 담당자가 이미 수행한 조치를 기록합니다. 외부 API나 매장 설비를 자동으로 실행하지 않습니다.
- 실제 PostgreSQL Outbox Worker가 있어도 프론트 작업 대기열은 해당 Worker와 연결되지 않았습니다. 실제 Worker 범위는 [Outbox 문서](serviq_outbox.md)를 확인합니다.
- Jev, Gemini/Ollama Runtime, LangGraph, Multi-Agent와 MCP의 실행 결과는 연결하지 않았습니다. 실행 추적은 제품 흐름을 확인하기 위한 예시입니다.
- 인증·역할별 운영자 권한·테넌트 격리와 전체 페이지의 서버 연동은 후속 범위입니다.

## 다음 단계

현재 확정한 화면 계약을 따라 검토, 작업 대기열과 설정의 서버 조회·명령을 연결하고 저장·감사 이력을 보강합니다. 이후 Jev → 공통 LLM Gateway → LangGraph → Multi-Agent → Harness/Loop → MCP 순서로 실행 경계를 확장합니다. Gemini와 Ollama는 공통 Gateway 뒤에 두고 각 화면은 실행 상태와 근거를 표시합니다.
